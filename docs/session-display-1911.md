# v1.9.11 세션 전환 재로그인·해상도 깜빡임·첫 영상 연결 수정

세 가지 모두 실제 PC 기록으로 원인을 확인했다. DESKTOP-DS8E56R(v1.9.5)과 192.168.195.141(v1.9.10, 실제 4K 모니터 + 가상 모니터)이다.

## 1. RDP로 쓰던 PC에서 Windows 로그인 후 끊기고 다시 로그인해야 함

### 원인

1. RDP 창만 닫으면 사용자 세션은 "끊김"으로 남고, 콘솔에는 로그인 화면용 임시 세션이 뜬다. 서비스는 Active 세션이 없으므로 콘솔에 대리 프로세스를 띄우고, 원격제어에는 그 로그인 화면이 보인다(정상 동작).
2. 거기서 로그인하면 Windows가 기존 사용자 세션을 콘솔로 옮기고 임시 세션을 없앤다. 그 안의 대리 프로세스(화면·입력·웹서버)도 함께 종료되고, 서비스가 새 세션에 다시 띄운다.
3. **화면 로그인(`rcsid` 쿠키)은 대리 프로세스 메모리에만 있었다.** 새 대리 프로세스는 그 쿠키를 모르므로 뷰어가 1.5초마다 다시 붙어도 `/ws`가 인증 없음으로 조용히 끊겼다. 뷰어는 "다시 연결합니다"에서 벗어나지 못했다.

기록: DESKTOP-DS8E56R 11-03 15:06에 세션 1(Winlogon)에서 대리 프로세스가 뜬 지 2초 만에 세션 2에서 다시 시작했다. "화면 연결 종료"도 남지 않았다(세션과 함께 강제 종료). MCP 인증은 v1.8.12부터 재시작을 넘어 유지되어 영향이 없었다.

### 변경

- `Auth.cs`: 화면 로그인을 `ProgramData\RemoteControl\credentials\screen-sessions.bin`에 함께 둔다.
  - 토큰이 아니라 **SHA-256만** 적는다. 파일이 새도 그것으로 로그인할 수 없다.
  - DPAPI(LocalMachine)로 봉인하고 현재 아이디·비밀번호 해시를 엔트로피로 섞는다. 비밀번호를 바꾸면 옛 파일은 풀리지 않고, 기존처럼 모든 접속을 끊는다.
  - SYSTEM·관리자만 읽는 `credentials` 폴더(`ConfigProtection.HardenDirectory`)에 둔다. 만료 8시간·로그아웃은 그대로이고 최대 256개까지 둔다.
  - 두 대리 프로세스가 겹쳐도 잠금 파일로 순서를 지킨다. 다른 프로세스가 만든 로그인은 파일이 바뀌었을 때만 다시 읽는다.
  - 이미 가진 Session 객체는 다시 읽어도 바꾸지 않는다(MCP 중계가 객체 동일성으로 확인한다).
  - 파일을 다루다 실패하면 그 프로세스는 예전처럼 메모리에만 둔다. 로그인이 막히지 않는다.
- `viewer.js`: 연달아 세 번 `/ws`를 열지 못하면 `/peers`로 로그인 상태를 묻는다. 로그인 화면이 돌아오면(만료·비밀번호 변경) 새로고침해 로그인 화면으로 보낸다. 응답이 없으면(대리 프로세스 재시작 중) 계속 기다린다.

## 2. 4K 적용 후 화면이 FHD ↔ 4K를 계속 오감 (특정 프로그램 실행 시 심해짐)

### 원인

- 대리 프로세스는 **저장된 해상도(screenw/screenh)를 5초마다 주 화면에 다시 강제**했다. 전체 화면 프로그램이 해상도를 자기 크기로 바꾸면 우리가 되돌리고, 프로그램이 다시 바꾸는 다툼이 끝나지 않았다. 그래서 그 프로그램을 띄우면 더 심해졌다.
- 저장된 해상도는 PC 하나에 하나다. 세션 1(RDP, `받는 크기: 2560x1440` 하나뿐)에서 고른 값이 세션이 콘솔로 옮겨진 뒤 실제 4K 모니터에 강제됐다. 기록: `화면 크기를 3840x2160 에서 2560x1440 로 맞췄습니다.`
- 그 화면이 받지 않는 크기도 5초마다 다시 시도했다. 기록에 `바꾸지 못했습니다`가 반복된다.
- 오류 설명 표가 한 칸씩 어긋나 있었다. 기록의 "다시 켜야 적용됩니다"는 실제로 `DISP_CHANGE_FAILED(-1)`, "드라이버가 거부"는 `DISP_CHANGE_BADMODE(-2)`였다.
- 해상도가 바뀔 때마다 GDI 영상 캡처 영역이 어긋나 GPU 영상이 끊기고 JPEG(`DD`)로 돌아갔다.

이 강제 기능은 원래 **모니터 없는 PC**용이었다. RDP를 끊고 tscon으로 콘솔에 되돌리면 Windows가 기본 화면 장치를 가장 작은 크기로 잡아 버리기 때문이다. 모니터(또는 가상 모니터)가 있으면 Windows가 해상도를 스스로 기억한다.

### 변경

- `Display.Target`: 모니터가 있거나(LooksHeadless가 아님) RDP 세션이면 강제하지 않는다. 원격 해상도 요청은 그 자리에서 적용하고 끝낸다.
- 모니터 없는 PC에서도 거부된 크기는 1분 뒤에 다시 시도한다(5초마다 반복하지 않는다).
- `Display.Explain`의 DISP_CHANGE 표를 바로잡았다.

## 3. 대리 프로세스가 뜬 뒤 첫 접속은 늘 JPEG(`DD`)로 남음

### 원인

대리 프로세스마다 처음 영상을 쓸 때 내장 helper와 FFmpeg(134MB)를 풀고 해시를 확인한다. 192.168.195.141에서는 첫 시도만 offer→answer가 12.5초, 다음 시도는 0.26초 걸렸다. 브라우저는 18초 안에 첫 영상이 없으면 JPEG로 돌아가므로, 인코더(`h264_qsv / GDI`)가 막 켜진 2.5초 뒤 포기했다. 그 뒤에는 새 화면 초기화가 올 때까지 다시 시도하지 않는다.

### 변경

- `RtcSession.Warm`: 대리 프로세스가 뜰 때 뒤에서 helper·FFmpeg 준비와 영상 방화벽 규칙을 미리 해 둔다. 걸린 시간을 기록에 남긴다(`GPU 영상 준비 완료 (n초)`). 실패하면 첫 영상 연결 때 다시 시도한다.

## 확인

- `bench/Test-ScreenSession.ps1`: 시험 프로그램을 별도 프로세스로 다시 띄워 확인한다. 새 프로세스에서 로그인 유지, 파일에 토큰 없음(해시만), 비밀번호 변경 시 무효, 로그아웃 전파, 다른 프로세스의 로그인 반영, Session 객체 유지, 전체 해제, 손상 파일 무시·교체, 만료 미복원, 저장 불가 시 메모리로 동작 — 12개 통과.
- `bench/ViewerControlTest.js`: 23개 통과. 추가한 4개는 성공하면 실패 횟수 초기화, 세 번 실패 시 로그인 확인, 로그인 유지 시 재시도 계속, 만료 시 로그인 화면이다.
- `bench/Test-StreamServer.ps1`: 33개 통과. 추가한 6개는 해상도 판단이다(모니터 PC 비강제, RDP 비강제, 모니터 없는 PC 복원·자동 FHD·미지원 생략, 거부 크기 1분 재시도).
- 기존 입력·캡처 41개, 내장 helper 파이프·종료 검사 통과.

## 한계

- 실제 RDP → 콘솔 전환과 전체 화면 프로그램과의 해상도 다툼은 이 변경을 설치한 PC에서 사람이 확인해야 한다.
- 세션이 바뀌는 몇 초 동안은 연결이 끊긴다(대리 프로세스가 세션과 함께 없어지는 Windows 구조). 외부망 터널도 새 대리 프로세스가 다시 연다.
- 가상 모니터만 있는 PC는 이제 저장된 해상도를 다시 강제하지 않는다. 재부팅 뒤 가상 모니터가 기본 크기로 돌아가면 원격에서 다시 고르면 된다.
- 해상도 변경은 여전히 **주 화면**에 적용되고 목록도 주 화면 기준이다. 보고 있는 화면이 주 화면이 아닌 다중 모니터 구성은 다음 과제로 남긴다.
- `Test-SecurityPolicy.ps1`·`Test-BuildSecurity.ps1`·`Test-InstallerUpgrade.ps1`은 관리자 권한이 필요해 비관리자 셸에서 실행하지 못했다(변경 전 코드도 같은 이유로 실패).
