# 끊김 시 입력 해제와 느린 회선 대응 — v1.6.1

연결이 끊길 때 서버가 좌·중·우 버튼과 보조 키를 무조건 해제하던 처리를 없앴습니다. 브라우저도 화면 밖에서 발생한 mouseup을 무조건 전송하던 경로를 수정했습니다. 각 접속이 실제로 누른 입력만 기록하고 해제합니다. 다른 접속이 누른 키를 함께 풀지 않으며, 정상적인 우클릭·키 반복·드래그는 유지합니다. 실제로 오른쪽 버튼을 누른 상태에서 연결이 끊긴 경우에는 그 버튼을 해제해야 하므로 정상적인 우클릭 해제가 발생할 수 있습니다.

포커스를 잃거나 파일·클립보드·PC 선택 화면을 열면 해당 접속의 입력을 해제합니다. 재접속 전 예약된 마우스 이동과 터치 드래그 타이머도 취소합니다. 소켓 정리보다 입력 해제를 먼저 처리하고, 통신이 완전히 멎으면 15초 읽기 제한으로 붙잡힌 입력을 정리합니다.

이 문서는 v1.6.1의 당시 측정 기록입니다. **v1.6.3에서는 고정 16KB 묶음과 타일 크기를 자동 조절하도록 변경했습니다.** 현재 동작과 4K 측정은 [4K 성능 기록](4k-performance.md)을 참조하세요.

## 화면 전송

- **브라우저 표시 확인:** JPEG 디코딩과 캔버스 갱신이 끝난 묶음에 ACK를 보냅니다. 동시에 확인을 기다리는 화면 묶음은 최대 두 개입니다. 소켓 Write가 성공했다는 이유로 옛 화면을 계속 밀어 넣지 않습니다.
- **최신 타일로 교체:** 아직 전송하지 않은 타일이 다시 바뀌면 최신 내용으로 교체합니다. 먼저 기다린 타일 순서를 유지해 특정 구역이 계속 누락되는 것도 막습니다.
- **작은 묶음:** 기본 16KB 단위로 보냅니다. JPEG 타일 하나가 더 크면 그 타일은 나누지 않고 보냅니다. 첫 화면은 모든 타일을 전달하고 이후에는 바뀐 부분만 보냅니다.
- **입력 수신 분리:** 느린 화면 송신 중에도 키·클릭·ACK를 받을 수 있도록 응답과 화면 설정 변경을 송신 스레드로 옮겼습니다.
- **마우스 이동 병합:** 고주사율 마우스의 이동은 브라우저의 다음 그리기 시점에 최신 좌표 하나로 합칩니다. 클릭·키 입력 전에 마지막 이동을 먼저 보내 순서를 유지합니다.
- **화질 자동:** 기본 `화질 자동`은 화면 변화가 많고 수신 확인이 밀릴 때 JPEG 화질을 낮춥니다. 움직임이 멎고 대기 화면을 보낸 뒤에는 선명하게 다시 그립니다. `화질 낮음/보통/높음` 수동 선택도 유지합니다. 해상도·화면 크기는 자동으로 바꾸지 않습니다.
- **그리기 순서:** 늦게 디코딩된 옛 타일이 새 타일이나 다른 PC 화면을 덮지 못하게 합니다. 크기·모니터 변경 이전의 좌표도 새 화면에 주입하지 않습니다.

확대 제스처나 화질 변경 후 화면이 정지해 있어도 새 화면을 다시 보내도록 보완했습니다. 화면 크기를 변경할 때는 Desktop Duplication을 다시 열어 새 버퍼를 전체 화면으로 채웁니다. 숨겨진 브라우저 탭은 화면 전송을 쉬고 돌아오면 갱신합니다.

새 브라우저와 서버가 ACK 기능을 협상합니다. 이전 하위 PC와의 브릿지도 기존 프로토콜로 연결할 수 있습니다. 개선된 서버 전송 제어를 쓰려면 실제 화면을 보내는 하위 PC에도 새 버전이 필요합니다. 연결된 쪽은 업데이트 후 페이지를 다시 열어 새 viewer.js를 받습니다.

## 측정

2026-09-23, 실제 로컬 TCP/WebSocket 연결에서 수신을 **1Mbps**, ACK 반환을 **80ms 지연**시켰습니다. 40개의 1KB 모의 타일이 계속 바뀌는 부하를 사용하고, 받은 타일의 캡처 시각부터 표시 모의 처리가 끝나는 시점까지 측정했습니다.

| 방식 | 평균 지연 | 95백분위 지연 |
|---|---:|---:|
| 이전 방식: ACK 없이 최대 96KB 묶음 | 3,254ms | 5,346ms |
| 8KB, 최대 두 묶음 | 68ms | 78ms |
| **16KB, 최대 두 묶음 — 적용** | **173ms** | **187ms** |
| 32KB, 최대 두 묶음 | 421ms | 423ms |

8KB는 지연이 가장 작았지만 같은 조건에서 전달량이 16KB보다 약 27% 적었습니다. 32KB는 화면 지연이 0.3초를 넘었습니다. 지연과 전달량을 함께 보고 16KB를 선택했습니다. 이 비교는 JPEG 화질 자동 조절 없이 전송 대기 제어만 측정했습니다.

**실제 WAN의 클릭부터 화면 표시까지를 측정한 결과는 아닙니다.** 실제 회선의 지연·손실, 캡처·JPEG 처리, 모바일 디코딩 시간은 추가로 영향을 줍니다. 대역폭이 부족할 때 과거 화면이 수초씩 쌓이는 문제를 줄이는 데 초점을 맞췄습니다.

## 검증과 빌드

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File bench\Test-Control.ps1
node bench\ViewerControlTest.js
node bench\ViewerLint.js
powershell -NoProfile -ExecutionPolicy Bypass -File bench\Test-StreamServer.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File bench\Test-SlowLink.ps1
.\빌드_setup.ps1  # 본체와 설치 파일을 모두 dist에 생성
```

입력/캡처/흐름 제어 25개, 브라우저 이벤트/비동기 디코딩 12개, 실제 서버 WebSocket 경로 11개를 검사합니다. 시험에서는 SendInput을 기록기로 교체하고 합성 화면을 사용하므로 실제 사용자의 화면과 마우스를 조작하지 않습니다. 운영 중인 서비스는 빌드 과정에서 중지하지 않습니다.
